# Proposal: Lambda-style Query API — Selector Lambdas

**Status:** Draft for review
**Scope decision:** Selector lambdas (not method references), full operation set (select / orderBy / expand / filter,
incl. nested NavQuery lambdas)
**Author note:** Produced after a full exploration of the current query machinery (`PropertyExpression` hierarchy,
generated constants, `Filterable`, `CollectionProperty.any/all` lambda plumbing).

---

## 1. Motivation

Today, read-shaping operations take static property constants:

```java
client.people()
    .

select(Person.FIRST_NAME, Person.LAST_NAME)
    .

orderBy(Person.USER_NAME.asc())
        .

filter(Person.FIRST_NAME.equalTo("Scott"))
        .

expand(Person.TRIPS.select(Trip.NAME))
        .

get();
```

This is already a metamodel pattern (jOOQ/JPA-style) and is compile-time safe. The proposal adds **selector lambdas** as
an additive ergonomic layer:

```java
client.people()
    .

select(p ->p.FIRST_NAME,p ->p.LAST_NAME)
        .

orderBy(p ->p.USER_NAME.

asc())
        .

expand(p ->p.TRIPS.

select(t ->t.NAME).

filter(t ->t.BUDGET.

greaterThan(500f)))
        .

filter(p ->p.FIRST_NAME.

equalTo("Scott"))
        .

get();
```

(Note on the original sketch `.select(t -> t.A, t.B)`: Java cannot mix a lambda and a bare expression in the same
varargs call — each argument carries its own lambda. The selector form above is the realizable version.)

**Why not method references** (`Person::getFirstName`)? Deriving the wire name backwards from a Java getter name has no
reliable inverse in this codebase: the sanitizers deliberately map hostile CSDL names to legal Java identifiers (`2FA` →
`_2FA`, `First-Name` → `first_name`, acronym splitting per lesson 85, case-collision dedup). `get_2FA` → `"2FA"` cannot
be recovered reliably, and a wrong guess produces a silently misspelled wire name (server 400 at best). Selector lambdas
keep wire names metadata-exact by reusing the generated constants.

**Why this is cheap:** property constants are immutable value-holders (`edmName` + `Class<E>`). A `Selector` view can
*share* the static instances — no new name state, no `x/` prefixes (unlike `Filterable`, whose names are `x/`-prefixed
for `any/all` lambda rendering and therefore unusable for `$select`). Cross-entity misuse becomes unrepresentable: `p`
is typed as the right `Selector`, so a foreign property is not even a member.

## 2. Design

### 2.1 Generated `Selector` inner class (per entity type)

Emitted by `EntityGenerator` (sibling of the existing `generateFilterableClass`), mirroring every property constant —
shared instances, no prefix, including single-valued navs (which `Filterable` omits):

```java
public static class Selector {
    public final StringProperty<Person> FIRST_NAME = Person.FIRST_NAME;
    public final NumberProperty<Person, Long> CONCURRENCY = Person.CONCURRENCY;
    public final EnumProperty<Person, PersonGender> GENDER = Person.GENDER;
    public final CollectionProperty<Person, Trip, Trip.Filterable> TRIPS = Person.TRIPS;
    public final NavProperty<Person, Photo> PHOTO = Person.PHOTO;
    // ... every constant the entity emits (scalars + collections + navs)
}
```

Complex types get no `Selector` in this pass (no request classes target them; boundary documented).

### 2.2 Request overloads (generated by `RequestGenerator`)

Collection requests gain (entity requests: `select` + both `expand` overloads only, mirroring today's surface):

```java

@SafeVarargs
public final PersonCollectionRequest select(
        java.util.function.Function<Person.Selector, ? extends PropertyExpression<? super Person, ?>>... selectors) {
    Person.Selector t = new Person.Selector();
    ... // apply each lambda once, delegate to the existing select(PropertyExpression...)
}

@SafeVarargs
public final PersonCollectionRequest orderBy(
        java.util.function.Function<Person.Selector, ? extends OrderExpression<? super Person, ?>>... expressions)

public PersonCollectionRequest expand(   // two overloads; the lambda body's return type disambiguates
                                         java.util.function.Function<Person.Selector, NavProperty<? super Person, ?>> nav)

public PersonCollectionRequest expand(
        java.util.function.Function<Person.Selector, NavProperty.NavQuery<? super Person, ?>> query)

public PersonCollectionRequest filter(
        java.util.function.Function<Person.Selector, ? extends FilterExpression<? super Person>> predicate)
```

Same `@SafeVarargs public final` conventions as the existing overloads. Delegation means all existing rendering (
transformation rejection in `select`, `getODataPath()` for `orderBy`, parenthesize-on-multiple `filter`) is inherited
unchanged.

### 2.3 Nested (NavQuery) lambdas — runtime change

For `expand(p -> p.TRIPS.select(t -> t.NAME))` the lambda parameter `t` must be a `Trip.Selector`. `NavProperty` today
has no way to obtain one, so:

- `NavProperty` / `CollectionProperty` gain a `Supplier<S>` **selectorFactory** (exact precedent: the
  `filterableFactory` added for `any`/`all` in decision 28). Generated nav constants pass `Trip.Selector::new`.
- `NavProperty` gains lambda overloads for `select` / `orderBy` / `filter`: each applies the factory once and delegates
  to the existing `PropertyExpression`-based methods.
- `NavQuery` (record) gains a component carrying the factory through, with a convenience constructor so existing call
  sites compile; same lambda overloads.

### 2.4 Type safety

- Cross-entity selection is unrepresentable: `p -> <member>` only resolves members of the right `Selector` (stronger
  than the constant API, where `select(Trip.NAME)` on `people()` is rejected via `? super E` generics — both mechanisms
  are compile-time).
- The `expand` two-overload resolution (lambda returning `NavProperty` vs `NavQuery`) is resolved by the lambda body's
  return type; pinned by a compile test.
- Existing constant API untouched — purely additive; no breaking change.

## 4. Verification

- New tests red → green.
- Full reactor offline green; `-Plive-tests` green (TripPin exercises lambda chains against the real service).
- Byte-identical generated output for all existing corpora apart from the additive emission (Selector classes +
  overloads), verified by the reactor's compile harnesses.

## 5. Out of scope (documented follow-ups)

- Method-reference derivation (`Person::getFirstName`) — no reliable inverse of the name sanitizers (see §1).
- `Selector` for complex types — only if nested-select-over-complex demand appears.
- `apply` / `$search` lambdas — no property-reference shape.

## 6. Implementation order

1. Runtime: `selectorFactory` on `NavProperty`/`CollectionProperty`/`NavQuery` + lambda overloads (red: rendering
   tests).
2. Core: `Selector` emission in `EntityGenerator` (red: content test).
3. Core: request overloads in `RequestGenerator` (red: content tests).
4. Compile referees + negative compile.
5. TripPin equivalence test + docs + AGENTS.md.
